# Безопасность

## 1. Область и предположения

Документ описывает меры безопасности `security-service`, `backend` и общих
интеграций. Предполагается, что production-трафик терминируется reverse proxy с
TLS; PostgreSQL, MinIO и Elasticsearch не публикуются в интернет.

Компоненты имеют разные зоны ответственности:

- `security-service` хранит пользователей, роли, подразделения и refresh-токены;
- `backend` хранит документы и бизнес-данные, ссылаясь на пользователей по UUID;
- оба сервиса проверяют access JWT локально;
- backend получает профили только через `/internal/**` с
  `X-Internal-Token`.

## 2. Что считается секретом

- пароли и строки подключения обеих PostgreSQL;
- `JWT_SECRET` (base64, не менее 32 случайных байт);
- `SECURITY_INTERNAL_TOKEN`;
- SMTP-логин и пароль;
- `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY`;
- пароль первичного администратора;
- приватный SSH-ключ сервера;
- Docker Hub token.

Секреты не хранятся в Git, compose-файлах, Dockerfile, README, тестах и логах.
В репозитории допустимы только имена переменных и заглушки `change-me-*`.

## 3. Расположение секретов

| Среда | Где хранятся |
|---|---|
| Локально | `.env` в корне (исключён `.gitignore`), IDE run configuration |
| CI | GitHub Actions Secrets, окружение `prod` |
| Production | `/home/ubuntu/.env` на сервере, права `600`, владелец deploy-пользователь |
| Контейнер | переменные окружения, переданные Compose |

`.env` на сервере не копируется в репозиторий и не перезаписывается деплоем.
Compose падает с понятной ошибкой, если обязательная переменная не задана.

## 4. Обязательная ротация после публикации репозитория

В истории Git ранее присутствовали реальные значения. **Считать их
скомпрометированными.** Удаление файла из текущего коммита не делает значения
безопасными.

Ротировать:

1. `JWT_SECRET` — сгенерировать новый (`openssl rand -base64 64`), обновить
   GitHub Secret/сервер, перезапустить **оба** сервиса. Все старые токены станут
   невалидными.
2. `SECURITY_INTERNAL_TOKEN` — новый случайный секрет; обновить security и
   backend одновременно.
3. Пароли обеих PostgreSQL — сменить в БД и в `.env`/секретах.
4. SMTP-пароль — сменить у почтового провайдера, обновить секрет.
5. MinIO root/access keys — создать новые ключи, перенести backend, отозвать
   старые.
6. Пароль администратора и всех демонстрационных пользователей — сменить или
   удалить демо-учётки в identity-базе.
7. Docker Hub token — перевыпустить, ограничить права.
8. SSH-ключ деплоя — перевыпустить, удалить старый из `authorized_keys`.

Опционально: очистить историю Git (BFG/filter-repo) и согласованно выполнить
force-push. Это ломает клоны и PR, поэтому выполняется только после ротации
секретов и согласования с командой. Ротация обязательна независимо от очистки
истории.

## 5. Аутентификация и авторизация

- Access-токен короткоживущий (`JWT_ACCESS_TOKEN_TTL`), refresh — длиннее и
  хранится в identity-БД с возможностью отзыва.
- Access-token содержит `uid`, `roles`, `department_id`,
  `managed_department_id`, `type=access`; backend строит `AuthenticatedUser`
  без обращения к БД.
- JWT-фильтр не логирует токен и возвращает JSON 401 на истёкший/невалидный
  access-токен.
- `/jwt/update` публичный для access-фильтра: refresh-токен проверяется
  отдельно, иначе истёкший access нельзя обновить.
- Роли проверяются `@PreAuthorize`; владение документом и доступ к файлам
  централизованы в `AuthorizationService`, а не дублируются в контроллерах и
  доменных сервисах.
- Скачивание файла проверяет принадлежность `contentUrl` доступной версии
  документа. Presigned URL не генерируется для произвольного пути.
- Подпись создаётся только для заявки текущего пользователя и только один раз;
  повторная подпись — 409.
- CORS: только явные origins из `CORS_ALLOWED_ORIGINS`; wildcard с credentials
  запрещён.

## 6. Внутренний API

`/internal/users/**` и `/internal/departments/**` не предназначены для
внешних клиентов.

- `InternalTokenFilter` сравнивает `X-Internal-Token` с
  `security.internal.token` через `MessageDigest.isEqual`.
- Если токен пуст, не задан или неверен, возвращается `401` без тела данных.
- Токен передаётся только по внутренней сети контейнеров; reverse proxy должен
  блокировать `/api/v1/internal/**` снаружи.
- `SECURITY_INTERNAL_TOKEN` не совпадает с `JWT_SECRET` и паролями.
- В дальнейшем общий токен можно заменить на mTLS или OAuth2 client
  credentials без изменения доменного кода backend.

## 7. Пароли и токены

- Пароли пользователей — BCrypt.
- Пароль администратора при bootstrap передаётся только через окружение и не
  выводится в лог. Bootstrap выполняется `security-service` только при явном
  `BOOTSTRAP_ADMIN_ENABLED=true`.
- JWT подписывается HMAC-ключом из `JWT_SECRET`; ключ не должен совпадать с
  паролями БД/почты.
- Refresh-токены хранятся в identity-БД; при выходе/ротации отзываются.
- Сравнение секретов не выполняется вручную; используются стандартные механизмы
  Spring Security и `MessageDigest.isEqual`.

## 8. Файлы и MinIO

- Bucket не публичный; доступ — через presigned URL с ограниченным TTL
  (`MINIO_PRESIGNED_URL_EXPIRY`, по умолчанию 15 минут).
- `MINIO_PUBLIC_ENDPOINT` должен указывать на внешний TLS-адрес MinIO; внутренний
  endpoint используется backend для загрузки/удаления, а presigned URL строится
  через публичный endpoint без сетевого запроса из контейнера.
- Имена объектов генерируются сервером, пользовательский ввод не становится
  путём без нормализации.
- При скачивании проверяется владелец/подписант, а не только знание URL.
- MIME/размер файла валидируются на уровне DTO/сервиса; ошибки не раскрывают
  внутренние пути.

## 9. Инфраструктура и сеть

- Контейнеры приложений работают от непривилегированного пользователя.
- Наружу публикуются API `8080`/`8081` и, при необходимости, MinIO public
  endpoint; PostgreSQL (обе базы), Elasticsearch и MinIO console доступны только
  локально.
- `/internal/**` не маршрутизируется через внешний reverse proxy.
- TLS — на reverse proxy; HSTS и security-заголовки включены Spring Security.
- SSH: только ключи, запрет root-логина, отдельный deploy-пользователь,
  минимальные sudo-права для Docker Compose.
- Firewall: разрешены 22/443 (и 80 для ACME), остальное закрыто.
- GitHub Environment `prod` защищён обязательным review; секреты доступны только
  этому окружению.
- Регулярно обновлять базовые образы, JDK, зависимости (Dependabot) и сервер.

## 10. Логи и мониторинг

- Не логировать: пароли, JWT, refresh-токены, `X-Internal-Token`, содержимое
  файлов, presigned URL целиком, персональные данные без необходимости.
- Логировать: успешные/неуспешные входы без секретов, отказы авторизации,
  повторные подписи, ошибки планировщика, результаты health-check.
- Рекомендуется централизованный сбор логов и алерты на 5xx, 401/403-аномалии,
  падение health, ошибки Liquibase.

## 11. Зависимости и CI

- `mvn verify` в CI обязателен для merge.
- JaCoCo контролирует покрытие (не ниже 90% строк в каждом модуле).
- Dependabot обновляет Maven/GitHub Actions/Docker-зависимости.
- Gitleaks (если включён) блокирует коммиты с похожими на секреты строками.
- CodeQL (если включён) анализирует Java на типовые уязвимости.
- Сторонние GitHub Actions закреплены по major-версии; для критичных workflow
  рекомендуется pin по SHA.

## 12. Реагирование на инцидент

1. Отозвать скомпрометированные секреты и токены, выпустить новые.
2. Перезапустить оба сервиса с новым `JWT_SECRET` (инвалидирует access-токены);
   при компрометации внутреннего токена обновить и `SECURITY_INTERNAL_TOKEN`.
3. Проверить логи входов, изменения документов и подписей за период.
4. При подозрении на утечку файлов — временно отключить MinIO public endpoint и
   проверить presigned-ссылки.
5. Уведомить владельцев данных; зафиксировать timeline и действия.
6. После стабилизации — ротация всех секретов, обновление зависимостей, ревью
   правил доступа.

## 13. Чек-лист перед merge

- [ ] В diff нет реальных паролей/токенов/ключей.
- [ ] Новые переменные описаны в `.env.example` без значений.
- [ ] Новые endpoint-ы закрыты авторизацией или осознанно публичны.
- [ ] `/internal/**` не попал во внешний прокси.
- [ ] Для новых файловых операций проверяется доступ.
- [ ] Ошибки не раскрывают stack trace и внутренние адреса.
- [ ] `mvn verify` зелёный, покрытие ≥ 90%.
